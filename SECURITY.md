# Security

## Reporting a vulnerability

Report security problems privately through GitHub's **Report a vulnerability** button on this repository's Security tab. Describe the defect with synthetic examples only: never include private financial data, keys, recovery codes or statements, in a report or in an issue.

## Local storage

Financial records, portfolio names, quantities, bank balances, API settings, imported statements and historical observations are encrypted together using CryptoKit AES-256-GCM. Authentication covers the document schema, vault ID and generation. Saves retain the previous encrypted generation (a file clone, size-checked when written and authenticated when opened) and use atomic replacement under a process lock, flushed to the drive with `F_FULLFSYNC`. Saves run one at a time in the order they were made, your edits ahead of background updates, each handed the vault when the one before finishes; preparing, encoding, encrypting and writing a save happen off the main thread, and the app shows the new document once it is saved. Every save is decoded again before it is sealed; one that wouldn't read back is refused and the last saved vault is kept. Amounts typed or imported must be below 10^24. If the current vault file is missing, can't be read, fails authentication, or opens but its contents don't decode though the build that saved it knew all their fields, unlock and recovery open the previous generation instead, save it back as current and tell you that the most recent change may be missing. Only a previous copy that opens is used, and the file it replaces is moved aside to `vault.uponly.damaged` (numbered if one is already there), never overwritten or deleted. Vault files, recovery files, journals and backup files are read only as regular files within their size limits, never through a symbolic link or from a pipe.

A vault folder holding any of `vault.uponly`, `vault.uponly.prev` or `recovery.wrapper`, or one beside which an unfinished restore's journal waits, is an existing vault: the app shows the unlock screen, not setup. Setup, like restoring from the welcome screen, writes only into a folder that is missing or holds just an Inbox with nothing but hidden files (hidden files such as Finder's aside, in the folder or in the Inbox), and checks again immediately before its first write. A welcome-screen restore removes a folder holding only Finder's `.DS_Store` files; a folder holding any other hidden file is moved beside it as “Vault (set aside <date and time>)”, never deleted.

If setup stopped after saving `recovery.wrapper` but before the vault, there is nothing to unlock, and unlocking offers **Start over**. It is offered, and checked again under the process lock just before it acts, only when the folder provably holds no vault data: nothing but the wrapper, an Inbox holding only hidden files, Finder's `.DS_Store` and a half-written wrapper. Start over moves the wrapper beside the vault folder as `Vault recovery.wrapper.unused` (numbered if one is already there), never deleting it, and setup begins again.

A file written by a newer version is refused and never mistaken for damage, so it is never rolled back to the previous copy; unlock and recovery say the vault was saved by a newer version of Up Only and leave its files untouched. The plain-text header's `format` says so for a new file layout. For a new document schema, the header carries an optional `schema` field, written only above schema 1: files of today's schema 1 are byte-for-byte as before, and earlier builds ignore the field. A build that raises the schema must write it. A file without it is authenticated with each schema this build knows, newest first. Each saved document also records `writerRevision`, the revision of the fields its build knows; a build that adds a field raises it. A document from a later revision is refused like a newer schema, even when it would decode, so an older build never saves over it and drops fields it doesn't know. A document that authenticates but doesn't decode, with this build's revision, an earlier one or none, is damage: unlock and recovery open the previous copy as above. Fields added later are optional when read, so older vaults keep opening.

A random vault key is stored in this Mac’s non-synchronizing, device-only data-protection Keychain with user-presence access control. Unlock uses LocalAuthentication with Touch ID or the Mac password. The recovery code is a separate randomly generated 256-bit secret that wraps the vault key; the app does not retain the recovery code. **Copy recovery code** puts the code on this Mac's clipboard only (not Universal Clipboard), marked concealed and transient, and clears it after a minute or when Up Only quits; the code itself isn't selectable, and its window is excluded from screen capture while it is shown. A code typed on the lock screen clears when the menu closes or after two minutes without typing.

**New recovery code** in Backup & security replaces the recovery code, the vault key, the vault's inbox key pair and its background signing key after Touch ID or the Mac password, so the old code, and any copy of the old wrapper, opens no vault file and no sealed background file saved from then on: the background configuration is rewritten and `.sealed` files encrypted to the old inbox key are deleted. The steps run in a crash-safe order: the new code's wrapper is saved as `recovery.wrapper.next` beside the old one; the vault is saved under the new key as its next generation, the previous copy keeping the same records under the old key; the Keychain then takes the new key, which commits the change; finally the previous copy is re-saved under the new key and the new wrapper replaces the old. If a step fails before the Keychain update, or authentication is cancelled, everything is put back and the old code and key stay in effect. If the change commits but its last step doesn't finish, Backup & security says so, and the next save, unlock or recovery finishes it; if the app stops partway, the next unlock or recovery finishes or undoes the change, using the key it opened the vault with. Until then Touch ID or the Mac password still opens the vault, and each code opens it through its own wrapper, so the old code may still open the previous copy. Backups exported earlier, OS backups of the app’s data and any `vault.uponly.damaged` file keep the old key and still open with the old code. Such an earlier backup can still be restored over the vault from Backup & security with the code it was exported with (see Backups).

Production builds require a provisioned Keychain access group, and Release builds carry no `get-task-allow` entitlement, so other processes can't attach a debugger to the unlocked app. Initial creation stores the protected key before publishing the first vault file. If an initial disk save fails before publication, its unpublished wrapper and key are removed so setup can retry. Access errors remain distinct from a missing key and don't send the user to recovery; a change of signing team or Keychain access group makes the key look missing, so the app offers recovery with the code. A cancelled or failed authentication while saving the key is treated as a cancellation. Recovery says the code was wrong only when a recovery file was read and the code didn't open it; otherwise it says what failed.

After initial vault creation, onboarding progress is saved inside its encrypted settings, including the current step, selected asset types and unfinished price-source choices. Provider keys entered during setup receive the same encryption as the rest of the vault. No provider is contacted until setup is complete; locking clears the draft's plaintext session state. Completion removes the onboarding draft. Import drafts stay in memory only; leaving an import discards it (after asking, if rows were changed), and locking clears it. Imports read only regular files you choose on this Mac, never web links; a chosen symbolic link is resolved first. Imported statement originals stay encrypted in the vault and its backups until you delete them with **Delete saved files…** under Statement files in Manage → Transactions; deleting keeps the transactions and duplicate detection, but doesn't remove the files from backups already made or from Time Machine, and the vault's previous-save copy holds them until the next save.

The app stays unlocked across popover dismissal and locks after five minutes of app inactivity (checked once a second by a timer App Nap can't defer; an open dialog gets no longer, and is closed with the lock), or immediately on screen lock (delivered even while the app is inactive), sleep or session resignation. User interaction restarts the idle period; background source updates do not. Lock invalidates authentication and discards the unlocked session: the decrypted document and everything worked out from it, drafts, editors, navigation, imports and their messages are held in one object that lock replaces with an empty one, cancelling its foreground refresh work and turning away saves still waiting their turn, so none of it reaches the next unlock. What outlives a lock is not vault data: the dashboard's chart range, holdings order, company-chart choice and height, and the background sources' last problems, which name only the source (“Accounting”, never a company). A session fence prevents an old operation from publishing into a later session. A save that hasn't begun replacing the file when the vault locks is refused, leaving the saved file as it was; one already replacing it finishes first, and the lock waits for it. Unlocked vault plaintext and transient fetched provider responses exist in process memory; Swift does not guarantee immediate zeroization of every copy.

Privacy mode is an encrypted vault preference, in every build. It replaces every value derived from your records (totals, balances, quantities, cost and average buy price, gains and losses in money, company figures, chart axis labels, hover cards and notes) with “••••” and its accessibility text with “Hidden value”, masks native amount inputs and their placeholders, and hides the switcher's breakdown and shares. Chart lines keep their shape and percentage changes stay; public market prices (unit prices, exchange rates) are shown as they are. If the setting can't be saved, values stay hidden for the rest of the unlock. It does not lock the vault or conceal account names, dates, transaction descriptions, or file names. Toggle it with the eye button or Shift–Command–P. Touch ID uses Apple’s embedded authentication view; Mac-password authentication remains system-owned.

The only plaintext the app writes outside the vault about your records is `diagnostics.txt`, and only when you press **Write diagnostics file** in Backup & security. It lists account, holding and company names, currencies, dates and counts for debugging chart gaps, with no amounts, ownership shares or bank profile IDs. It is created readable by your user only (mode 600); remove it with **Delete diagnostics file** when you no longer need it. With `UPONLY_MEASURE_UNLOCK=1` set, the app also writes `unlock-timing.json`, which holds timings only. macOS may remember the last folder used in a save or open dialog in the app's container preferences; that is a folder path, not vault data.

The sandbox allows outbound HTTPS and files explicitly selected by the user. There is no application server, analytics SDK or automatic cloud backup. OS backups may include the encrypted vault. A vault replaced by a restore stays, still encrypted, in its own folder beside the current one until you delete it. FileVault is complementary protection for the Mac itself.

## Network

No provider is contacted until setup is complete, and each lookup happens only with its source switched on: coin search and the Add form's current and past-day prices included. With a source off, coin search offers only coins already known and exact CoinGecko IDs, and costs are typed by hand. In the standard build, the only app-requested hosts are `api.coingecko.com`, `api.frankfurter.dev`, `api.gold-api.com`, `api.binance.com` and `forex-data-feed.swissquote.com`; the private build adds `api.wise.com` (which also supplies its exchange rates), `oauth2.googleapis.com`, `sheets.googleapis.com` and `www.googleapis.com`. Redirects are refused. Sessions are ephemeral with no persistent cookies or URL cache. Response sizes and deadlines are bounded; prices, asset IDs, currencies and timestamps are validated when fetched and again when a sealed background packet is applied. Coin IDs are checked and percent-encoded before they go into a request path. Frankfurter v2 requests validate the returned base/quote pair and retain exact source decimals. Individual currency failures preserve successful observations; cancellation and failed vault writes publish none of the pending update.

The providers see requests and network metadata, including IP addresses, from one session with a fixed `User-Agent`, so requests that name coins can be linked to the rest. With its source on: CoinGecko sees coin search text, a request for the 250 (or 500) largest coins for current prices, and a coin's ID for any coin outside those, for history, for intraday charts and for purchase-day prices (with the date). Binance sees one request for all its prices, single-symbol price requests, and trading pairs with dates for history, charts and purchase days (for gold, PAXG). Swissquote and Gold API see metal symbols. Frankfurter, and Wise in the private build, see currency codes and date ranges. History is requested only for the days an asset was held. No provider receives quantities, bank balances, account names, portfolio names, statements or vault keys.

The same process also performs networking; this release does not claim process separation. After a normal setup unlock, selected source identifiers (held coins, currencies and metals), source switches, provider credentials, the vault's public inbox key and a dedicated signing key live in an app-specific Keychain configuration for background refresh. It is kept in the data-protection Keychain in the app's own access group, on this Mac only (never synchronized), readable after the Mac's first unlock so refreshes can run while the vault is locked. A configuration found in the login keychain, where earlier versions kept it, is never read, only deleted; the next unlock saves it again. The configuration fetches only for the vault whose file header is on disk; Start over, a new vault, or a restore or recovery of a different vault deletes it along with its sealed packets and schedules. This configuration never contains the vault key or inbox private key. Background requests do not authenticate or decrypt the vault and cannot extend the inactivity deadline.

Each source's last successful background response is encrypted with a fresh AES-GCM key wrapped to the vault's public inbox key and signed with the dedicated signing key. Atomic mode-600 `.sealed` files contain only envelopes, and they and the `.schedule` files are read size-capped, as plain files only. A trusted signer stored inside the encrypted vault, its vault ID, signature and authenticated encryption are checked after normal unlock, and the contents validated, before observations are applied. A new signing key deletes older sealed packets. Disabled sources and replayed packets are ignored; source timestamps remain intact. A failed source preserves its previous cache. While running and awake, exchange rates refresh every 15 minutes, crypto and metal prices hourly, and in the private build company accounting hourly and Wise every 12 hours; the app cannot refresh while quit or asleep. Historical catch-up requires unlock.

Historical fetches and their checkpoints remain inside the encrypted vault. Backfill uses dated quantities and source timestamps; publication gaps remain explicit. Metal quantities are fine grams, distinct from crypto token identifiers. Current metal prices need no account. Gold history comes from Binance's PAXG pair; other metals' history uses a Gold API key only if an earlier version saved one (Gold API then sees their symbols and date ranges), and otherwise gaps between saved prices are filled. Provider credentials are sent only to their designated host in request headers, never query strings. History and live data are committed together after validation; lock cancels preparation and fences stale results.

## Backups

Export produces a directory ending in `.uponlybackup`, containing ciphertext, the recovery wrapper and a checksummed manifest. Export can replace an earlier Up Only backup after you confirm **Replace** in the save dialog; it never replaces a vault or any other folder. Restore requires the recovery code that was current when the backup was exported. From the welcome screen it needs an empty destination and refuses to overwrite an existing vault; the restored folder is moved into place before the Keychain takes its key, so if the app stops in between, the code entered opens it through recovery, and if the Keychain refuses, the copy is removed. **Restore from a backup** in Backup & security can replace an existing vault: the backup is read and verified and the code must open it before anything changes, a vault with records asks for confirmation, and Touch ID or the Mac password is required. The vault’s session is then closed so nothing else can be saved, a journal naming the folders (`Vault.restore.journal`: names and a checksum, no key or code) is written beside it, its folder is moved, not deleted, to “Vault (replaced <date and time>)” beside it, and the backup is written to a staging folder, flushed, every file (including the previous copy and pending imports) read back, and moved into the empty location. The Keychain takes the backup's key last, which commits the restore, and nothing can fail after that. Before it, any failure removes the restored copy, puts the original folder back, saves the vault's own key again if a Keychain update was tried, and locks. If the app stops partway, the next unlock or recovery settles the restore before opening anything: with nothing in the vault's place, the original folder goes back; with the backup's untouched copy there, it stands if the Keychain's key (or, on recovery, the code entered) opens it, and otherwise it is removed and the original goes back. A code that opens neither changes nothing. Each path ends with the Keychain key and the files agreeing, and the replaced folder is never removed. A journal that can't be read, or names anything unexpected, is left untouched: if the vault folder holds the vault, unlock and recovery open it and say the journal needs attention; otherwise they refuse and say a restore didn't finish. Staging folders a stopped restore left (`Vault.restore-<ID>`) that no journal names are removed at the next unlock or recovery.

The backup may be an earlier one of the same vault, from before a recovery-code change; it restores with the code it was exported with. The replaced folder stays encrypted. A different vault's key stays in the Keychain; a replaced copy of the same vault shares its Keychain entry, which now holds the backup's key, so that copy opens with the recovery code it had when it was replaced. Keep the code and backup separately: either alone is insufficient to decrypt the data.

Vault files are capped at 128 MiB. A save that would exceed that limit is refused without replacing the last saved vault. Save, export and restore share the same size limits so a successful export stays within the restore reader’s limits.

## Repository

No personal or financial data, API credentials, signing certificates, recovery codes, vault files or user containers belong in this repository, including its tests and history; tests and the separate preview target use fictional names and figures only. Production starts empty. `.gitignore` excludes vault, backup, sealed-cache, diagnostics, statement and signing files, and CI refuses tracked files that look like them or like secrets, build-script phases, packages, and entitlements beyond sandbox, network client, user-selected files and the Keychain group. CI runs on a self-hosted runner on the owner's build Mac, registered to this repository only; because the repository is public, a fork pull request's workflow needs the owner's approval before it runs, its jobs skip pull requests from other repositories, and the workflow uses no secrets.

## Limits

Encryption cannot protect information already visible to someone using an unlocked app, a compromised operating system, or malware with sufficient access to the running process. Keychain and Touch ID depend on macOS and hardware availability. Financial observations may be stale or incomplete; the interface labels those conditions. Opening an older generation, and the unauthenticated key ID of a waiting recovery file, need write access to the app's container, which can already delete the vault. Keychain keys left by a failed setup or Start over open nothing without their vault and are kept.

## Private Wise build

`UPONLY_PERSONAL` is an optional local compilation flag. The public app excludes the Wise credential reader, connector and setup UI. The private build uses a separate bundle identifier and vault directory. Its read-only API token, selected profile IDs and bootstrap artwork live in a Keychain item, never in the app bundle or repository. The app keeps it in the data-protection Keychain in its own access group (this Mac only, never synchronized, readable after first unlock); an item provisioned into the login keychain is moved there on first read and deleted from the login keychain only after the move is saved. The app does not write that token into the vault or backups.

Selected profile names and bootstrap artwork appear on the private welcome screen before vault unlock and stay loaded when the popover closes. Financial records and pending imports still clear when the vault locks.

Private Wise requests are GET-only to `api.wise.com`, with ephemeral sessions, no cookies/cache, no redirects and bounded response/pagination limits. The locked prefetch fetches balances and activities and seals them to the vault's inbox key; they are applied only after unlock. Lock cancels foreground requests and fences pending results; no response from an earlier session can commit into a later one. Applied activities, linked profile identifiers and account artwork are stored in the encrypted vault. A failed sync preserves the last saved document. Native balances come from the balance endpoint, not transaction sums. The activity feed may require user review for transfers; it is not a replacement for official statements.

## Private accounting

Private accounting credentials and source mappings remain in a separate Keychain item, kept like the Wise item: data-protection Keychain, this Mac only, moved there from the login keychain on first read. Native requests use Google OAuth JWT exchange and read-only Sheets/Drive scopes, bounded responses and no redirects. Credential reads refuse authentication UI, so background work cannot prompt for a vault unlock. The service account's workbook permissions remain external to the app. Accounting prefetch runs hourly, while locked too; a failure is reported only as “Accounting”. Saved company results, effective ownership periods, source provenance and refresh warnings live in the encrypted vault (or sealed prefetch until unlock). Public builds exclude this connector and credential access, and ignore accounting packets.
