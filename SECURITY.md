# Security

## Local storage

Financial records, portfolio names, quantities, bank balances, API settings, imported statements and historical observations are encrypted together using CryptoKit AES-256-GCM. Authentication covers the document schema, vault ID and generation. Saves retain the previous encrypted generation (a file clone, size-checked when written and authenticated when opened) and use atomic replacement under a process lock, flushed to the drive with `F_FULLFSYNC`. Saves run one at a time in the order they were made, your edits ahead of background updates, each handed the vault when the one before finishes; preparing, encoding, encrypting and writing a save happen off the main thread, and the app shows the new document once it is saved. If the current vault file is missing, can't be read or fails authentication, unlock and recovery open the previous generation instead, save it back as current and tell you that the most recent change may be missing. Only a previous copy that opens is used, and the file it replaces is moved aside to `vault.uponly.damaged` (numbered if one is already there), never overwritten or deleted.

A vault folder holding any of `vault.uponly`, `vault.uponly.prev` or `recovery.wrapper`, or one beside which an unfinished restore's journal waits, is an existing vault: the app shows the unlock screen, not setup. Setup, like restoring from the welcome screen, writes only into a folder that is missing or holds just an empty Inbox (hidden files such as Finder's aside), and checks again immediately before its first write.

If setup stopped after saving `recovery.wrapper` but before the vault, there is nothing to unlock, and unlocking offers **Start over**. It is offered, and checked again under the process lock just before it acts, only when the folder provably holds no vault data: nothing but the wrapper, an empty Inbox, Finder's `.DS_Store` and a half-written wrapper. Start over moves the wrapper beside the vault folder as `Vault recovery.wrapper.unused` (numbered if one is already there), never deleting it, and setup begins again.

A file written by a newer version is refused and never mistaken for damage, so it is never rolled back to the previous copy; unlock and recovery say the vault was saved by a newer version of Up Only and leave its files untouched. The plain-text header's `format` says so for a new file layout. For a new document schema, the header carries an optional `schema` field, written only above schema 1: files of today's schema 1 are byte-for-byte as before, and earlier builds ignore the field. A build that raises the schema must write it. A file without it is authenticated with each schema this build knows, newest first. Fields added to the encrypted document later are optional when read, so older vaults keep opening; saving writes the same bytes as before.

A random vault key is stored in this Mac’s non-synchronizing, device-only data-protection Keychain with user-presence access control. Unlock uses LocalAuthentication with Touch ID or the Mac password. The recovery code is a separate randomly generated 256-bit secret that wraps the vault key; the app does not retain the recovery code.

**Create a new recovery code…** in Backup & security replaces both the recovery code and the vault key after Touch ID or the Mac password, so the old code, and any copy of the old wrapper, opens no vault file saved from then on. The steps run in a crash-safe order: the new code's wrapper is saved as `recovery.wrapper.next` beside the old one; the vault is saved under the new key as its next generation, the previous copy keeping the same records under the old key; the Keychain then takes the new key, which commits the change; finally the previous copy is re-saved under the new key and the new wrapper replaces the old. If a step fails before the Keychain update, or authentication is cancelled, everything is put back and the old code and key stay in effect. If the app stops partway, the next unlock or recovery finishes or undoes the change, using the key it opened the vault with; until then Touch ID or the Mac password still opens the vault, and each code opens it through its own wrapper. Backups exported earlier, OS backups of the app’s data and any `vault.uponly.damaged` file keep the old key and still open with the old code. Such an earlier backup can still be restored over the vault from Backup & security with the code it was exported with (see Backups).

Production builds require a provisioned Keychain access group. Initial creation stores the protected key before publishing the first vault file. If an initial disk save fails before publication, its unpublished wrapper and key are removed so setup can retry. Access or provisioning errors remain distinct from a missing key and do not automatically send the user to recovery. The authenticated vault schema is unchanged.

After initial vault creation, onboarding progress is saved inside its encrypted settings, including the current step, selected asset types and unfinished price-source choices. Provider keys entered during setup receive the same encryption as the rest of the vault. These draft choices do not enable network sources until setup is completed; locking clears their plaintext session state. Completion removes the onboarding draft. Import drafts stay in memory only; leaving an import discards it (after asking, if rows were changed), and locking clears it.

The app stays unlocked across popover dismissal and locks after five minutes of app inactivity, or immediately on screen lock, sleep or session resignation. User interaction restarts the idle period; background source updates do not. Lock invalidates authentication and discards the unlocked session: the decrypted document and everything worked out from it, drafts, editors, navigation, imports and their messages are held in one object that lock replaces with an empty one, cancelling its foreground refresh work and turning away saves still waiting their turn, so none of it reaches the next unlock. What outlives a lock is not vault data: the dashboard's chart range, holdings order, company-chart choice and height, and the background sources' last problems. A session fence prevents an old operation from publishing into a later session, and a save still in progress when the vault locks is refused, leaving the saved file as it was. Unlocked vault plaintext and transient fetched provider responses exist in process memory; Swift does not guarantee immediate zeroization of every copy.

The only plaintext the app writes outside the vault about your records is `diagnostics.txt`, and only when you press **Write diagnostics file** in Backup & security. It lists account and holding names, currencies and dates for debugging chart gaps, with no amounts, and is readable by your user only (mode 600). Delete it when you no longer need it.

The sandbox allows outbound HTTPS and files explicitly selected by the user. There is no application server, analytics SDK or automatic cloud backup. OS backups may include the encrypted vault. A vault replaced by a restore stays, still encrypted, in its own folder beside the current one until you delete it. FileVault is complementary protection for the Mac itself.

## Network

Networking is opt-in. In the standard build, the only app-requested hosts are `api.coingecko.com`, `api.frankfurter.dev`, `api.gold-api.com`, `api.binance.com` and `forex-data-feed.swissquote.com`; the private build adds `api.wise.com` (which also supplies its exchange rates). Redirects are refused. Sessions are ephemeral with no persistent cookies or URL cache. Response sizes and deadlines are bounded; prices, asset IDs, currencies and timestamps are validated before committing. Frankfurter v2 requests validate the returned base/quote pair and retain exact source decimals. Individual currency failures preserve successful observations; cancellation and failed vault writes publish none of the pending update.

The providers see requests and network metadata, including IP addresses. Binance sees, for current prices, one request for all its prices; history and past-day requests name a trading pair and dates (for gold, PAXG). CoinGecko sees, for current prices, only a request for the 250 (or 500) largest coins, unless a coin outside those is held; its history requests name the coin. Swissquote sees a metal symbol. Wise, in the private build, also sees currency codes and date ranges for rates. Frankfurter sees currency codes and historical date ranges. Gold API sees metal symbols (and date ranges, only if a history key was saved by an earlier version). No provider receives quantities, bank balances, account names, portfolio names, statements or vault keys.

The same process also performs networking; this release does not claim process separation. After a normal setup unlock, selected source identifiers, source switches, provider credentials, the vault's public inbox key and a dedicated signing key live in an app-specific Keychain configuration for background refresh. It is kept in the data-protection Keychain in the app's own access group, on this Mac only (never synchronized), readable after the Mac's first unlock so refreshes can run while the vault is locked; a configuration saved by an earlier version in the login keychain is moved there once, only while nothing is saved in the new place, and the old item is deleted after the new one is saved. Until then the old item stays and is still used; an item that can't be read at that moment is left for the next attempt, never taken for missing. This configuration never contains the vault key or inbox private key. Background requests do not authenticate or decrypt the vault and cannot extend the inactivity deadline.

Each source's last successful background response is encrypted with a fresh AES-GCM key wrapped to the vault's public inbox key and signed with the dedicated signing key. Atomic mode-600 `.sealed` files contain only envelopes. A trusted signer stored inside the encrypted vault, its vault ID, signature and authenticated encryption are checked after normal unlock before observations are applied. Disabled sources and replayed packets are ignored; source timestamps remain intact. A failed source preserves its previous cache. Current observations refresh on a 15-minute target while running/awake; the app cannot refresh while quit or asleep. Historical catch-up and activity sync require unlock.

Historical fetches and their checkpoints remain inside the encrypted vault. Backfill uses dated quantities and source timestamps; publication gaps remain explicit. Metal quantities are fine grams, distinct from crypto token identifiers. Current metal prices need no account, but automatic historical catch-up requires the user's free Gold API key. Provider credentials are sent only to their designated host in request headers, never query strings. History and live data are committed together after validation; lock cancels preparation and fences stale results.

## Backups

Export produces a directory ending in `.uponlybackup`, containing ciphertext, the recovery wrapper and a checksummed manifest. Export can replace an earlier Up Only backup after you confirm **Replace** in the save dialog; it never replaces a vault or any other folder. Restore requires the recovery code that was current when the backup was exported. From the welcome screen it needs an empty destination and refuses to overwrite an existing vault. **Restore from a backup…** in Backup & security can replace an existing vault: the backup is read and verified and the code must open it before anything changes, a vault with records asks for confirmation, and Touch ID or the Mac password is required. The vault’s session is then closed so nothing else can be saved, a journal naming the folders (`Vault.restore.journal`: names and a checksum, no key or code) is written beside it, its folder is moved, not deleted, to “Vault (replaced <date and time>)” beside it, and the backup is written to a staging folder, flushed, read back and moved into the empty location. The Keychain takes the backup's key last, which commits the restore, and nothing can fail after that. Before it, any failure removes the restored copy, puts the original folder back, saves the vault's own key again if a Keychain update was tried, and locks. If the app stops partway, the next unlock or recovery settles the restore before opening anything: with nothing in the vault's place, the original folder goes back; with the backup's untouched copy there, it stands if the Keychain's key (or, on recovery, the code entered) opens it, and otherwise it is removed and the original goes back. A code that opens neither changes nothing. Each path ends with the Keychain key and the files agreeing, and the replaced folder is never removed.

The backup may be an earlier one of the same vault, from before a recovery-code change; it restores with the code it was exported with. The replaced folder stays encrypted. A different vault's key stays in the Keychain; a replaced copy of the same vault shares its Keychain entry, which now holds the backup's key, so that copy opens with the recovery code it had when it was replaced. Keep the code and backup separately: either alone is insufficient to decrypt the data.

Vault files are capped at 128 MiB. A save that would exceed that limit is refused without replacing the last saved vault. Save, export and restore share the same size limits so a successful export stays within the restore reader’s limits.

No financial files, API credentials, signing certificates, recovery codes or user containers belong in this repository. Production starts empty; only the separate preview target contains synthetic records.

## Limits

Encryption cannot protect information already visible to someone using an unlocked app, a compromised operating system, or malware with sufficient access to the running process. Keychain and Touch ID depend on macOS and hardware availability. Financial observations may be stale or incomplete; the interface labels those conditions.

Do not publish private financial data, keys or statements in an issue. A security report should describe the defect with synthetic examples only.

## Private Wise build

`UPONLY_PERSONAL` is an optional local compilation flag. The public app excludes the Wise credential reader, connector and setup UI. The private build uses a separate bundle identifier and vault directory. Its read-only API token, selected profile IDs and bootstrap artwork live in a local Keychain item, never in the app bundle or repository. The app does not write that token into the vault or backups.

Selected profile names and bootstrap artwork appear on the private welcome screen before vault unlock and stay loaded when the popover closes. Financial records and pending imports still clear when the vault locks.

Private Wise requests are GET-only to `api.wise.com`, with ephemeral sessions, no cookies/cache, no redirects and bounded response/pagination limits. Activity sync runs only while unlocked; current balances may prefetch into sealed cache while locked. Lock cancels foreground requests and fences pending results; no response from an earlier session can commit into a later one. Completed activities, linked profile identifiers and account artwork are stored only in the encrypted vault. A failed sync preserves the last saved document. Native balances come from the balance endpoint, not transaction sums. The activity feed may require user review for transfers; it is not a replacement for official statements.

Privacy mode is an encrypted, backward-compatible vault preference. It replaces displayed financial values and accessibility text with placeholders, masks native amount inputs, and hides chart tooltip/accessibility values while keeping trends and navigation usable. It does not lock the vault or conceal account names, dates, transaction descriptions, or file names. Toggle it with the eye button or Shift–Command–P. Touch ID uses Apple’s embedded authentication view; Mac-password authentication remains system-owned.

## Private accounting

Private accounting credentials and source mappings remain in a separate local Keychain item. Native requests use Google OAuth JWT exchange and read-only Sheets/Drive scopes, bounded responses and no redirects. Credential reads refuse authentication UI, so background work cannot prompt for a vault unlock. The service account's workbook permissions remain external to the app. Saved company results, effective ownership periods, source provenance and refresh warnings live in the encrypted vault (or sealed prefetch until unlock). Public builds exclude this connector and credential access.
